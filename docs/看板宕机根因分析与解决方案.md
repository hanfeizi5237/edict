# 监控看板宕机根因分析与彻底解决方案

## 一、问题现象

监控看板（`http://172.16.30.107:7899/`）频繁宕机，每次崩溃后需要人工发现 + 手动重启。

## 二、根因分析（5 层）

### 🔴 根因 1：无进程守护机制
- 看板服务用 `nohup python3 server.py &` 裸跑，**崩溃后永不复活**
- 无 systemd 服务注册，无进程管理器（supervisor/pm2）
- 服务器重启后服务不会自启

### 🔴 根因 2：无独立健康检查
- 现有 watchdog（`openclaw-watchdog.sh`）只监控 Gateway，**完全不管看板**
- 没有定时探测 7899 端口或 HTTP 健康端点
- 服务挂了只能等皇上发现或太子巡查

### 🔴 根因 3：内存压力（OOM Kill）
- dmesg 记录显示服务器发生过 OOM Kill（apt-get 被杀，消耗 12GB 内存）
- 看板服务无内存限制，可能与其他进程竞争内存
- 无内存保护策略

### 🟡 根因 4：代码层面风险
- `server.py` 2701 行单文件，40 处 `except Exception` 但均为兜底捕获
- 使用 `ThreadingHTTPServer`，但部分后台线程无超时保护
- 文件操作使用 `atomic_json_read/write`（有锁保护，OK）
- 请求体限制 1MB（合理）

### 🟡 根因 5：手动重启依赖
- `restart_dashboard.sh` 文件不存在（之前提交的 commit 引用了但不存在）
- 每次挂掉需要人工 SSH 执行重启命令

## 三、已实施的彻底解决方案

### ✅ 1. systemd 进程守护
- 文件：`/etc/systemd/system/edict-dashboard.service`
- **自动重启**：`Restart=always`，崩溃后 5 秒自动拉起
- **崩溃保护**：5 分钟内最多重启 5 次（`StartLimitBurst=5`）
- **开机自启**：`WantedBy=multi-user.target`
- **内存保护**：`MemoryMax=1G`，`MemoryHigh=768M`

### ✅ 2. 健康检查 Watchdog
- 文件：`/root/edict/scripts/dashboard-watchdog.sh`
- **执行频率**：每 5 分钟（cron）
- **三层检测**：systemd 状态 → 端口监听 → HTTP 健康探测
- **自动恢复**：最多 3 次重试（systemd restart → 杀进程重拉）
- **飞书告警**：宕机时发橙色告警，恢复后发绿色通知，3 次失败发红色告警

### ✅ 3. 内存保护
- systemd cgroup 限制：最大 1GB，高水位 768MB
- 防止看板吃光内存被 OOM Kill

## 五、常用管理命令

```bash
# 查看状态
systemctl status edict-dashboard

# 重启服务
systemctl restart edict-dashboard

# 查看日志
journalctl -u edict-dashboard -f --no-pager

# 查看 watchdog 日志
tail -f /root/edict/logs/dashboard-watchdog.log

# 手动触发健康检查
/root/edict/scripts/dashboard-watchdog.sh
```
